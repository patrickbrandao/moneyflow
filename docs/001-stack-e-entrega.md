# 001 — Stack e entrega

| Tema | Decisão |
|---|---|
| Frontend | Template da skill `purple-skills-public:web-interface-admin-with-canva`: React 19, Vite, TypeScript, Tailwind 4, React Flow, cmdk, lucide. Seguir as regras de design da skill (tokens, sem hex em componentes, um único acento, sem sombra em superfície fixa). O acento é azul nos dois temas (o roxo do template foi trocado em 2026-10-11, tarefa 007); nenhuma cor da interface, do logo ou da paleta de categorias `--port-1`…`--port-12` fica na faixa roxa (matiz 250°–320°). |
| Backend | Node + TypeScript, Fastify, Drizzle ORM (só consultas; schema gerado do banco), Zod. |
| Banco | PostgreSQL 18 + pgvector, em `database/`, gerido pelo agente DBA ([016](016-banco-de-dados.md)). Migrations SQL com dbmate, testes pgTAP. Anexos também no Postgres (`bytea`, tabela própria, limite por arquivo). |
| Repositório | Monorepo pnpm em `github.com/patrickbrandao/moneyflow`: `apps/web`, `apps/server` (modos `api` e `worker`), `packages/shared` (schemas Zod, tipos, definições das tools dos agentes), `packages/db` (schema Drizzle gerado do banco). O banco fica em `database/`, fora dos workspaces. |
| Qualidade | Biome (lint/format), pgTAP no banco, Vitest + Testcontainers (Postgres 18 real) para regras financeiras, Playwright nos fluxos principais. Dois níveis de verificação: rápida no desenvolvimento (`pnpm verify:quick`, só o que mudou, integração no Postgres local) e completa sob pedido, antes de PR e release e sempre no CI (`pnpm verify:full`). |
| Imagem | Imagem única `tmsoftbrasil/moneyflow`: a API serve o SPA compilado; o mesmo artefato roda como `api` ou `worker`. |
| Cabeçalhos de segurança | Toda resposta da API leva `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` e `Referrer-Policy: same-origin` (hook `onSend` em `apps/server/src/security-headers.ts`). O HTML do SPA leva a CSP `default-src 'self'`, `script-src 'self'` mais o hash sha256 de cada `<script>` inline do `index.html` (o do tema; calculado no boot a partir do `index.html` compilado, então mudar o script não exige mexer na CSP), `style-src 'self' 'unsafe-inline' https://fonts.googleapis.com` (atributos `style` do React e do markdown saneado), `font-src 'self' https://fonts.gstatic.com data:`, `img-src`/`media-src 'self' data: blob:` (prévias, gravação, exportações; imagens externas no markdown não carregam), `worker-src 'self' blob:` (worker do pdf.js), `connect-src 'self'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'` e `frame-ancestors 'none'`. Sem `unsafe-eval`: o console desliga o JIT do Zod (`@moneyflow/shared/zod-jitless`, primeiro import do `main.tsx`). Uma resposta que já define a própria CSP (o `sandbox` dos downloads de anexo) fica com ela; sem SPA servido, um HTML sai só com `frame-ancestors 'none'; object-src 'none'; base-uri 'self'`. |
| Logs e erros | Log em JSON (pino) na API e no worker. Erro de consulta sai sem os parâmetros (senha, token do bot, chave de IA) e sem o `DETAIL` do Postgres, que repete a linha recusada: ficam o SQL, o código e a mensagem (`loggableError`/`errorText` em `apps/server/src/errors.ts`, aplicados pelo serializador e por um gancho do pino em `src/log.ts`; tarefa 070). Toda resposta leva `x-request-id` (UUID, ou o `X-Request-Id` do proxy quando há `TRUSTED_PROXIES` e o formato vale), que também vai em cada linha do log da requisição (`reqId`); o 500 devolve `requestId` no corpo e o console mostra "Algo deu errado (código abc12345)" (tarefa 186). |
| Limite do corpo | JSON e texto até 1 MB (o `bodyLimit` do servidor; os parsers da aplicação não definem o próprio). Cada rota que precisa de mais declara o seu: os uploads crus (`config.rawUpload`) 20 MB, o `/mcp` ~7 MB (o `upload_file` com até 5 MB em base64, [027](027-tools-de-controle-total.md)) e a importação do backup o `BACKUP_MAX_UPLOAD_MB`. Acima do limite, 413 `payload_too_large`, sem ler o corpo quando há `content-length`: o login e o webhook do Telegram, sem sessão, não seguram mais de 1 MB por requisição (tarefa 106). |
| Configuração | Variáveis de ambiente lidas uma vez por `loadConfig` (`apps/server/src/config.ts`; lista e padrões no `.env.example`). As numéricas passam por `intEnv`: vazia ou ausente = o padrão; valor que não é inteiro, ou fora da faixa da variável, impede o boot com a mensagem que a cita (tarefa 110), em vez de virar 0 ou `NaN` em silêncio. `NOTIFY_AT` fora de `HH:MM` também impede o boot. |
| Ambiente local | Docker Compose: o compose da raiz inclui `database/docker-compose.yml` (Postgres 18 + pgvector), aplica as migrations num one-shot (dbmate) e sobe `api` e `worker`. O Postgres dessa pilha tem volume próprio e sai na porta 5433, só em loopback (`STACK_DB_BIND`, padrão `127.0.0.1`; `0.0.0.0` o expõe na rede de propósito), para conviver com o banco de desenvolvimento de `database/` (5432), usado por `pnpm dev`. Segredos locais de integrações (a chave do CNPJ Aberto, spec 003) ficam em `.local/` (fora do git e da imagem), carregados pelo compose e pelo `pnpm dev`. A API publica a porta direto, sem proxy: `TRUSTED_PROXIES` fica vazio (o IP do cliente é o da conexão, [002](002-usuarios-e-permissoes.md)); atrás de um proxy reverso, liste-o nessa variável. |
| CI/CD | GitHub Actions: lint, typecheck, testes e build em PRs/main, com o token só de leitura, prazo por job e as actions pelo SHA; o schema Drizzle e o `schema.sql`/`privileges.sql` conferidos contra as migrations. Em tag `v*`: o CI inteiro no commit da tag e, se passar, build multi-arch (amd64+arm64) e push `:X.Y.Z` e `:latest` (só na maior tag; secrets `DOCKERHUB_USERNAME` e `DOCKERHUB_TOKEN`). `make release` para push local (conta `tmsoftbrasil` autorizada na máquina), depois do `release-check` ([018](018-versoes-e-publicacao.md)). Node 26 no `.nvmrc`, o mesmo no CI e na imagem. |
| Locale | Interface pt-BR com strings centralizadas (i18n-ready), fuso `America/Sao_Paulo`, `dd/mm/aaaa`, `R$ 1.234,56`. Código e banco em inglês. |
| Moeda | Só BRL, valores em centavos (`bigint`). |
