# 018 — Versões e publicação

## Versões

- A série atual é **0.1.x**: a primeira publicação é `v0.1.0`, e cada nova release incrementa o último número (`v0.1.1`, `v0.1.2`…). Mudar o número do meio ou chegar à `1.0.0` é decisão do dono do produto.
- A versão fica em `package.json` (raiz) e é a fonte do `make release`. A tag git `vX.Y.Z` aponta para o commit publicado.
- Cada release publica `tmsoftbrasil/moneyflow:X.Y.Z` (amd64 + arm64) e move `:latest` para ela só se `vX.Y.Z` for a maior tag: uma correção de uma versão antiga não move o `:latest`.

## Como publicar

- **Desta máquina** (padrão hoje): atualizar a versão em `package.json`, commitar, criar a tag `vX.Y.Z` nesse commit, rodar `make release` com a conta `tmsoftbrasil` logada no Docker e fazer push do commit e da tag. O `make release` passa antes pelo `release-check` (tarefa 078), que recusa a árvore com alteração não commitada e o `HEAD` que não é a tag `v<versão do package.json>`, e roda `pnpm verify:full` (`VERIFY_ARGS="--e2e"` acrescenta o e2e, com a pilha no ar). A imagem é construída do commit (`git archive HEAD`), nunca da árvore de trabalho.
- **Pelo CI**: `release.yml` faz o mesmo numa tag `v*`. Primeiro roda o CI inteiro no commit da tag (o `ci.yml` como workflow reutilizável: lint, typecheck, testes, pgTAP, imagem e e2e); só depois constrói, com SBOM e proveniência. Recusa a tag que não é a versão do `package.json`, e só publica se os secrets `DOCKERHUB_USERNAME` e `DOCKERHUB_TOKEN` existirem no repositório.
- **Versões fixas** (tarefas 163, 184 e 187): o Node do `.nvmrc` é o do desenvolvimento, do CI e da imagem (`FROM node:<versão>-bookworm-slim@sha256:…`); as actions vão pelo SHA do commit; o dbmate e a imagem do banco têm versão completa (e digest, [016](016-banco-de-dados.md)). O `scripts/check-versions.mjs` confere tudo isso no CI. A produção (projeto externo) deve usar a imagem do banco com a mesma tag e o mesmo digest de `database/docker/Dockerfile`, ou registrar as versões dela.

## Ambientes

- Este repositório roda **só em Docker local** (desenvolvimento, testes e validação).
- O setup do serviço e a publicação em produção (servidor, domínio, HTTPS, backup) ficam num **projeto externo**, que consome a imagem do Docker Hub. Este repositório não contém scripts de deploy de produção.
- **Proxy reverso da produção (`TRUSTED_PROXIES`)**: desde a tarefa 050, a API só aceita o `X-Forwarded-For` de proxies listados em `TRUSTED_PROXIES` (IPs, CIDRs ou `loopback`/`linklocal`/`uniquelocal`; vazio = nenhum, [002](002-usuarios-e-permissoes.md)). **Antes de atualizar a produção para a versão com essa mudança, configure `TRUSTED_PROXIES` no projeto externo com o IP/CIDR do proxy reverso (ou da rede Docker dele).** Sem isso o sistema continua seguro, mas todo mundo aparece com o IP do proxy: os logins dividem um único limite de `LOGIN_RATE_LIMIT` por minuto (pode travar o login com muita gente entrando ao mesmo tempo) e `sessions.ip` grava o IP do proxy. Não use as faixas privadas inteiras se a porta for publicada direto pelo Docker: o peer chega com o IP privado do gateway e o contorno voltaria.
- **Dono do banco sem superusuário (tarefa 054)**: a restauração do dump passou a rodar `pg_restore` → `psql --single-transaction` e chama `restore_reset_default_privileges()` (migration 0055); a imagem precisa do `psql` (já vem no `postgresql-client-18`). Funciona com a produção como está (superusuário na `DATABASE_OWNER_URL` e nas migrations; a restauração só avisa no log). Para tirar o superusuário: criar no Postgres da produção um papel dono `LOGIN NOSUPERUSER NOCREATEROLE NOCREATEDB` (o `database/docker/initdb/03-owner-role.sh` faz isso e passa a posse dos objetos já criados, com `OWNER_DBS=<banco>`), apontar a `DATABASE_OWNER_URL` e o `DATABASE_URL` do dbmate para ele e só então rodar as migrations seguintes. Um dump gerado com o superusuário como dono dos objetos e restaurado pelo papel dono pode falhar nas entradas DEFAULT ACL do superusuário: faça um dump novo depois da troca.
- **Sessão ociosa e cookie (tarefa 066)**: `SESSION_IDLE_HOURS` (padrão 72; `0` desliga) derruba a sessão sem uso nesse tempo; atrás de HTTPS, `COOKIE_SECURE=true` (a API avisa no boot se a URL pública é HTTPS e o cookie não é seguro).
- **Cabeçalhos de segurança (tarefa 065)**: a API manda `X-Frame-Options`, `nosniff`, `Referrer-Policy` e a CSP do SPA ([001](001-stack-e-entrega.md)); se o proxy da produção já define uma CSP, as duas valem juntas (o navegador aplica as duas), então confira que a do proxy não é mais permissiva que necessário nem conflita.
- **Parada e saúde dos processos (tarefa 107)**: no SIGTERM, o worker para de agendar, devolve à fila as execuções de agente que estavam na chamada ao modelo (o próximo worker as reserva na hora, sem esperar a reserva velha de 2 min e sem gastar tentativa), espera a passada em andamento (o envio do Telegram termina marcado) e sai em até `SHUTDOWN_GRACE_MS` (padrão 8 s) mais uma folga de 1,5 s; a API fecha os streams SSE antes de fechar o servidor (o console reconecta). No projeto externo, dê ao serviço do worker um `stop_grace_period` acima do `SHUTDOWN_GRACE_MS` (o compose daqui usa 30 s). O healthcheck da imagem (`/app/healthcheck.mjs`) decide o modo pelo argumento do processo ou `MODE` (`docker run … worker` funciona sem `MODE`): na API, `/api/health`; no worker, o batimento que o laço de mensagens grava a cada passada que chega ao banco (`WORKER_HEARTBEAT_FILE`, padrão na pasta temporária), saudável até 3 × `MESSAGE_INTERVAL_MS` (mínimo 90 s). O compose de produção não deve sobrescrever o healthcheck do worker com um `exit 0`.

## Validação da série 0.1.x

O usuário valida por uso livre numa base limpa. Achados e pedidos viram tarefas em `tasks/` ([017](017-tarefas-entre-agentes.md)); cada lote corrigido pode virar uma nova release 0.1.x.
