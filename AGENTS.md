# AGENTS.md

Guia para agentes de código (Claude Code, Codex e outros) neste repositório.

## Especificações

@docs/INDEX.md

As especificações em `docs/nnn-titulo.md` são a fonte da verdade do produto. Antes de implementar ou alterar algo, leia as que tratam do assunto, a partir do índice acima. Quando uma decisão mudar, atualize a especificação correspondente e o `docs/INDEX.md` na mesma mudança. Uma especificação nova segue a numeração `nnn` com zeros à esquerda.

## Banco de dados

Tudo o que é banco (PostgreSQL 18 + pgvector) fica em `database/` e é responsabilidade exclusiva do subagente **dba** (`.claude/agents/dba.md`, regras em [database/AGENTS.md](database/AGENTS.md)). Não edite `database/`: descreva a necessidade e delegue ao dba. Detalhes em [docs/016-banco-de-dados.md](docs/016-banco-de-dados.md).

## Tarefas entre agentes (`tasks/`)

Achados do usuário e pedidos de revisão/correção entre agentes viram arquivos `tasks/nnn-titulo.md` com status no cabeçalho, listados em [tasks/INDEX.md](tasks/INDEX.md). Toda tarefa tem um agente designado: o subagente **triage** analisa, reproduz e designa o executor — **dba** para `database/`, **app** para o resto —, que corrige com testes e fecha a tarefa. Se você encontrar algo fora do seu escopo, abra uma tarefa em vez de contornar. Detalhes em [docs/017-tarefas-entre-agentes.md](docs/017-tarefas-entre-agentes.md). Versões e publicação: [docs/018-versoes-e-publicacao.md](docs/018-versoes-e-publicacao.md).

## Verificação (dois níveis)

- **Rápida, o padrão** enquanto se desenvolve e ao concluir uma tarefa: `pnpm verify:quick`. Olha só o que mudou desde o ponto em que o branch saiu do `main` (commits, alterações e arquivos novos): Biome nos arquivos alterados, typecheck dos pacotes afetados e dos que dependem deles, testes do shared relacionados, testes de integração dos arquivos tocados (`test/x.test.ts` alterado, ou o de mesmo nome de `src/.../x.ts`) contra o Postgres local, sem container, e o pgTAP dos testes de `database/tests/` alterados. Não roda build, e2e nem a suíte inteira. Se a heurística não achar o teste certo, passe-o: `pnpm verify:quick -- test/contracts.test.ts -t "renovação"`. Toda mudança continua vindo com o teste que a cobre; o que muda é quanto da suíte roda.
- **Completa, só quando o usuário pedir** ("verificação completa", "rode tudo"), antes de abrir PR e antes de release: `pnpm verify:full` (lint, typecheck, todos os testes com Testcontainers, build e todo o pgTAP; `--e2e` acrescenta o Playwright com a pilha no ar, `--local` roda a integração no Postgres local). O CI roda sempre o completo.
- Modo local dos testes de integração (`MONEYFLOW_TEST_DB=local`, `pnpm test:local`): usa o Postgres de desenvolvimento (`make -C database up`, porta 5432); as migrations ficam no banco modelo `moneyflow_it_tpl`, refeito quando `database/migrations` muda, e cada execução recria `moneyflow_it` por cópia dele (começa limpo). Não usa `moneyflow_test`, que é do pgTAP. Duas execuções locais ao mesmo tempo disputam o mesmo banco.

## Comandos

Node 22.12+ e pnpm 9 (`corepack enable`). Copie `.env.example` para `.env` na raiz.

```bash
pnpm install
make -C database migrate seed   # banco de desenvolvimento (Postgres 18 na 5432), migrations e seeds
pnpm dev                        # API (http://localhost:3001) + Vite (http://localhost:5174, encaminha /api)
pnpm dev:worker                 # worker (séries, faturas de cartão, sessões, mensagens, agentes de IA) em modo watch
pnpm lint                       # Biome (lint + formato); `pnpm format` corrige
pnpm typecheck                  # tsc em todos os pacotes
pnpm test                       # unitários (shared) + integração da API
pnpm test:unit                  # só packages/shared
pnpm test:integration           # API contra Postgres 18 real: o Testcontainers builda database/docker e aplica as migrations
pnpm test:local                 # a mesma integração no Postgres local (5432), sem container: banco limpo copiado de um modelo migrado
pnpm verify:quick               # verificação rápida do que mudou no branch (o padrão; veja Verificação)
pnpm verify:full                # verificação completa (só quando pedido, antes de PR e release; --e2e, --local)
pnpm build                      # SPA (apps/web/dist) + bundle da API/worker (apps/server/dist/main.mjs)
pnpm db:pull                    # regenera packages/db/src/generated depois de uma migration nova (nunca edite à mão)
docker compose up --build -d    # pilha completa: Postgres (5433), migrations, api (http://localhost:3000, serve o SPA) e worker
pnpm e2e                        # Playwright contra a pilha no ar (E2E_BASE_URL, padrão http://localhost:3000)
# Os e2e de mensagens sobem uma Bot API falsa na porta 18081 (E2E_TELEGRAM_PORT): suba a pilha apontando para ela
TELEGRAM_API_BASE=http://host.docker.internal:18081 docker compose up --build -d
# Os e2e de agentes sobem um provedor de IA falso na porta 18082 (E2E_LLM_PORT) e o cadastram com
# base_url http://host.docker.internal:18082 (E2E_LLM_BASE); nada chama uma API de IA real.
node e2e/fakes/fake-llm.ts 18082   # o mesmo provedor falso, à mão, para testar o console (Anthropic: base_url http://host.docker.internal:18082)
# O e2e do Telegram de entrada (visao.spec.ts) sobe outro provedor falso na 18083 (E2E_LLM_TELEGRAM_PORT) e chama o webhook direto,
# com o segredo que a Bot API falsa (e2e/fakes/fake-telegram.ts, a mesma dos testes de integração) recebeu no setWebhook.
node e2e/fakes/fake-telegram.ts 18081   # a Bot API falsa, à mão (setWebhook, getFile e o download, botões; nada vai ao Telegram)
make release                    # build multi-arch e push de tmsoftbrasil/moneyflow:<versão> e :latest
```

Teste isolado:

```bash
pnpm --filter @moneyflow/server exec vitest run test/titles.test.ts -t "estorno"   # integração, um caso (Testcontainers)
pnpm --filter @moneyflow/server test:local test/titles.test.ts -t "estorno"       # o mesmo no Postgres local, em segundos
pnpm --filter @moneyflow/shared exec vitest run test/documents.test.ts           # unitário, um arquivo
MONEYFLOW_TEST_DATABASE_URL=postgres://moneyflow_app:moneyflow_app@localhost:5432/moneyflow_test pnpm test:integration  # banco já migrado, sem Testcontainers
pnpm --filter @moneyflow/e2e exec playwright test -g "baixa"                     # um e2e
pnpm --filter @moneyflow/server exec vitest run test/agents.test.ts -t "retomada"  # agentes (provedor e MCP falsos)
pnpm --filter @moneyflow/server exec vitest run test/autonomous.test.ts -t "Telegram"  # F15: tarefas, conciliação com IA e Telegram
```

O banco tem comandos próprios (`make -C database test`, pgTAP) em [database/AGENTS.md](database/AGENTS.md).

## Estrutura

- `apps/server` (Fastify, `@moneyflow/server`): um único artefato, `node dist/main.mjs api|worker` (ou `MODE`). `src/routes` (REST em `/api`), `src/services` (regras e transações; recebem um `ServiceContext`), `src/services/tx.ts` (`withTx`: TODA escrita roda numa transação que define o ator da auditoria; `deleteOrArchive` com savepoint), `src/authz/access.ts` (autorização central: admin global vê tudo; os demais por `caixa_members` editor/viewer), `src/auth` (sessão em cookie httpOnly, `sessions.id` = sha256 do token, admin inicial por `ADMIN_*`), `src/errors.ts` (erros do banco 23514/23505/23503/42501 traduzidos para pt-BR), `src/worker.ts` (séries até 12 meses à frente, com advisory lock; faturas de cartão do horizonte e, com `CARD_AUTO_CLOSE=true`, o fechamento automático; num segundo laço, a cada `MESSAGE_INTERVAL_MS`, as mensagens do Telegram e o sino). Fase 2: `card-core.ts`/`cards.ts` (cartão), `statements.ts`/`reconciliation.ts` (extratos e conciliação), `attachments.ts`, `audit.ts` (histórico e fechamento de mês; o da entidade inclui `entity_tag_links`), `title-entry.ts` (PIX, NF-e, ponto de extensão da leitura por IA), `calendar.ts`. Fase 3: `reports.ts` (relatórios e `scopeCaixas`: caixas legíveis + cartões das pagadoras escolhidas), `flow.ts` (canvas e posições), `messages.ts` (destinos, assinaturas, outbox, enviar teste e `deliver`), `message-worker.ts` (laço de mensagens: produtor de eventos com dedup, notificações do sino, consumidor da outbox, `emitAgentEvent` para a F4), `notifications.ts` (sino), `integrations/telegram.ts` (Bot API em `TELEGRAM_API_BASE`). ## Regras da aplicação

- A aplicação conecta como `moneyflow_app` e nunca seleciona `users.password` (use `userColumns`); login só por `auth_login()`, revelar só por `admin_reveal_password()`. Nunca devolva senha pela API nem a inclua em logs, exports ou tools de agente. Única exceção: o backup do admin (spec 019), que lê os segredos pelas funções `admin_*` e os grava no arquivo exportado.
- Fluxos que tocam várias tabelas (espelho, baixa com duas pernas, transferência, estorno, compra e parcelas, fechamento de fatura) rodam numa transação só: as checagens do banco são deferidas para o COMMIT (docs/016).
- Toda escrita usa `withTx(ctx, …)` (nunca `ctx.db.insert/update/delete` direto): a transação começa com `set_config('app.user_id', …, true)` e `app.actor_kind` (`agent` + `app.agent_run_id` na F4). Um teste de integração confere que nada escrito pela API sai como ator `system`.
- Toda permissão passa por `Access` (`assertRead`/`assertWrite`/`assertAdmin`); serviços nunca consultam `caixa_members` por conta própria. As tools dos agentes (F4) reaproveitarão os mesmos serviços.
- UI: só tokens (nenhum hex em componente), um único acento azul (o roxo do template foi trocado; nenhuma cor da interface fica na faixa roxa), sem sombra em superfície fixa; cor de categoria = `var(--port-N)` com N = `color_slot` (1–12). Textos em pt-BR vindos de `@moneyflow/shared` (`t`).
- Dinheiro em BRL, em centavos inteiros; datas de negócio como `YYYY-MM-DD` no fuso `America/Sao_Paulo`.
- Relatórios e canvas: as funções do banco recebem a lista de caixas; passe sempre `scopeCaixas(ctx, pedidas)` (só caixas legíveis, 404 se pedir outra).
- `message_destinations`: NUNCA `SELECT *` nem `RETURNING` sem colunas (o papel da aplicação não lê `bot_token`; 42501). O token é write-only como a senha: nunca devolvido pela API, nem em logs, auditoria, exportações (fora o backup do admin) ou tools de agente.
- Segredos da IA (`ai_providers.api_key`, `mcp_servers.secret_headers`, `user_api_tokens.token_hash`): NUNCA `SELECT *` nessas tabelas (42501); liste colunas. Grave e nunca devolva; leia só pelas funções do banco (`ai_run_provider_credentials`, `ai_capability_credentials`, `ai_run_mcp_headers`, `ai_embedding_credentials(provedor)`, `admin_*`, `api_token_authenticate`). Fora de logs, auditoria, eventos de SSE e resultados de tools; só o backup do admin (spec 019) os exporta.
- Chamadas ao provedor de IA: sempre por `createLlmClient(credenciais, log)`/`embed`/`transcribe`/`speak(…, log)` com o `RequestLogBase` (provedor, execução ou usuário, `log_bodies`, tentativas da configuração), nunca um SDK solto; o uso gravado em `ai_usage` leva o `request_id` devolvido. `ai_requests`/`ai_request_attempts` não têm DELETE para a aplicação (só `ai_requests_purge`).
- Provedor por inferência (spec 024): o texto é `ai_agents.provider_id/model`; visão, embeddings, áudio→texto e texto→áudio vêm de `ai_agent_inferences`, sempre resolvidos por `agents/inferences.ts` (modelo nulo = padrão do provedor). Ao gravar um provedor, `default_models` só com as chaves das flags ligadas; o Anthropic com `base_url` exige `default_models.text`. Gravar em `ai_embeddings` exige o par registrado (`ai_embedding_indexes_touch()`) e o `provider_id`.
- Agentes: tools novas entram em `AGENT_TOOLS` (shared, com `category` e, quando for o caso, `adminOnly`/`secrets`/`producesFile`) e no `TOOL_HANDLERS` (server), sempre sobre os serviços (com `Access`), com `preview` nas escritas (e nas leituras, que também podem ficar em `ask` num kit). Quem decide allow/ask é o kit do agente (spec 021); tool nova não entra sozinha em kit nenhum. Segredos (spec 027): o campo fica FORA do schema da tool; a prévia declara `secretFields`, o valor chega em `meta.secrets` pela requisição de decisão e a API executa a tool ali (`executeSecretTool`), entregando o resultado ao worker pelo evento `tool_result` com `prepared`; o worker nunca executa tool de segredo, e o valor nunca vai a resultado, evento, confirmação, auditoria ou log. Arquivo gerado (`producesFile`): o handler devolve `{ file }` e o runtime grava o anexo e o liga à mensagem `tool` da sessão. O loop grava em transações curtas e nunca segura transação durante a chamada ao modelo. Em `ai_messages`, nunca selecione `search_tsv` (use `MESSAGE_COLUMNS`). Sessões (spec 026): no máximo uma `chat` ativa por (usuário, agente), garantida no banco; quem fala com o fio (console, Telegram, tarefas) usa `ensureActiveSession`/`sendToAgent`; mensagem e execução só na ativa (a finalizada é somente leitura e não volta: bifurque); finalizar e bifurcar pedem o parar da execução ativa na mesma transação.
- Toda execução nova de agente passa por `assertCanStartRun` (spec 028: limite por minuto e orçamento do mês; `429` com `retry-after` ou `budget_exceeded`); o runner confere o orçamento antes de cada chamada. Os testes de integração sobem com `AI_RUNS_PER_MINUTE=1000`.
- Chave do CNPJ Aberto (`CNPJ_ABERTO_API_KEY`, spec 003): segredo local em `.local/cnpjaberto.env` (fora do git e da imagem; o compose da raiz e o `pnpm dev` o carregam). Nunca a versione, devolva pela API nem a registre em logs.
- Telegram de entrada (spec 029): o token do bot fora da outbox só por `telegram_inbound_bot_token(destino)` (`inboundToken` em `services/messages.ts`), nunca devolvido nem registrado; o segredo do webhook fica só como hash (`webhook_secret_hash`, conferido por `telegram_webhook_authenticate`). Ligar a entrada chama `setWebhook` na mesma transação; desligar, desativar ou arquivar desliga no mesmo UPDATE e chama `deleteWebhook`. As respostas aos chats privados vão direto pela Bot API (nunca pela outbox, que é do chat do destino). A URL pública vem de `telegram.public_base_url` (vence `PUBLIC_BASE_URL`) e só vale com HTTPS.
- Enfileirar mensagem sempre com `dedup_key` e `ON CONFLICT (destination_id, dedup_key) DO NOTHING`; notificação com `ON CONFLICT (user_id, dedup_key) DO NOTHING`.
